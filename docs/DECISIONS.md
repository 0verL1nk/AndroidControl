## ADR-021：中继支持 TLS + 证书指纹固定

**日期**：2026-10-24
**状态**：已采纳

**决策**：中继增加 `--tls-listen/--tls-cert/--tls-key`，与明文监听并存、共用同一份
配对表。手机端用**自签证书 + SHA-256 指纹固定**：配了指纹就走 TLS，只接受指纹
相同的证书（主机名不参与校验）。公网部署时明文监听绑 `127.0.0.1`，只给隧道/反代。

**理由**：
- "不自建 CA、不依赖公共 CA"最符合自托管场景：一张自签证书、一串指纹，部署者自己掌控。
- 指纹即身份，换证书必须显式改配置——不会被误签的根证书悄悄降级。
- 明文与 TLS 共用协议逻辑与配对表，网页端（Cloudflare WSS）与手机端可以混用。

**代价**：证书轮换需要同步更新两端指纹；TLS 握手多一到两次往返（连接只建一次）。

**放弃的备选**：
- 反向代理终止 TLS：过程更简单，但节点上多一个常驻组件，且 App 侧仍无法校验身份。
- 公共 CA（Let's Encrypt）：需要域名、续期与 80/443 端口，对"自签就够"的场景是负担。

## ADR-020：配对失败限速放在中继，不靠外部 fail2ban

**日期**：2026-10-24
**状态**：已采纳

**决策**：中继内置按口令哈希（直连时含来源 IP）的失败计数与锁定窗口
（`--max-fails` / `--fail-window` / `--lock-secs`，默认 10 次/10 分钟 → 锁 10 分钟），
锁定期间 `FIND` 直接回 `ERR` 且不再通知长辈端；成功配对清零；审计日志只记哈希前 8 位。
`ASK`（查求助）不计数。

**理由**：
- 6 位数字在公网上必须防暴力试；放在协议层可以精确按"哈希"而不是 IP 计（经隧道时 IP 全是回环）。
- 锁定时不惊动长辈端，避免攻击流量变成长辈手机上的骚扰。
- `ASK` 被控制端周期性轮询，`NONE` 不是猜口令，计入会误伤正常使用。

**代价**：锁定是全局的——知道哈希的攻击者可以让合法用户在锁定窗口内连不上；
10 分钟窗口下这个代价可接受（比被猜中低得多）。

## ADR-019：网页控制端用 WebSocket + WebCodecs，不引入第三方播放器

**日期**：2026-10-20
**状态**：已采纳

**决策**：新增 `web/`（Next.js 16）浏览器控制端。中继在一个端口上同时提供 HTTP 与
WebSocket（`/ws`）；页面用浏览器原生 WebCodecs 解码 H.264，触摸/按键直接复用 scrcpy 控制消息。
不引入 jmuxer/mse 之类的播放器库。

**理由**：
- 浏览器与 App 共用同一套协议，中继只多了一层 WebSocket 适配（约 200 行），
  不需要为网页单独做一套流媒体服务。
- WebCodecs 是标准 API，延迟低、无需转封装（Annex-B → AVCC 只有几十行）。
- 不引入第三方 JS，符合"无遥测、少依赖"的原则。

**代价**：WebCodecs 只在安全上下文（HTTPS / localhost）可用，所以网页端需要 TLS 入口；
文档给出 Cloudflare Tunnel 与 Caddy 反代两种做法。

**放弃的备选**：
- MSE + jmuxer：兼容面更广，但要内置第三方库并把裸流封装成 fMP4。
- 在节点上转码推流：多一跳、多一份 CPU，且破坏端到端延迟。

## ADR-018：控制端与被协助端合并为同一个 App

**日期**：2026-10-20
**状态**：已采纳

**决策**：`:agent` 与 `:controller` 改为 Android 库，新增 `:app` 作为唯一安装包。
首页同时展示"我的配对码（打开即待命）"和"输入对方口令去协助"。

**理由**：用户在任何一台手机上装的都是同一个 App，角色由使用方式决定；
降低分发与理解成本（不用解释"你要装控制端还是长辈端"）。
被协助不再需要按"开启"——打开首页即自动待命，符合"长辈端零操作"。

**放弃的备选**：
- 保持两个 APK：安装选择容易出错，代码也要维护两套清单/图标。

**影响**：
- 包名变为 `dev.ling.app`；从旧版升级需要重新授权 Shizuku 与一次性权限。
- 两个库的图标/主题资源冲突，统一由 `:app` 引用控制器库的图标与 `Theme.Controller`；
  主题补齐为完整的 Material 3 ColorScheme（含深色），并修正了根节点缺 Surface 导致的
  深色文字不可见问题。

## ADR-017：双向语音用 PCM 直传，复用中继的 `audio` 角色

**日期**：2026-10-20
**状态**：已采纳

**决策**：语音对讲采用 16 kHz / 单声道 / 16-bit PCM，20 ms 一帧（640 字节），
两端复用一个共享的 `:audio` 模块；中继只增加一个 `audio` 角色，一条连接双向传输。

**理由**：
- 不引入原生 Opus 依赖（NDK/JNI 会显著增加两端构建复杂度），也没有编解码延迟；
  256 kbps 的带宽在家庭 Wi-Fi 和蜂窝网络上都可接受。
- 语音的瓶颈是网络往返而不是码率；PCM 让"采集→发送→播放"的路径最短，最好排障。
- 两端实现完全相同的模块（`audio/VoiceSession`），避免"参数不一致导致噪声"这类问题。
- 用 `VOICE_COMMUNICATION` 音源 + 回声消除，长辈不会听到自己。
- 长辈端前台服务声明 `microphone` 类型，应用退到后台后录音权限不被系统收回。

**放弃的备选**：
- WebRTC：功能完备但依赖重，还要引入信令与 ICE，超出"自用、少依赖"的定位。
- Opus：省带宽，但需要原生库；当前没有带宽压力。

**影响**：
- 中继是明文转发，语音同样不加密——与屏幕内容处于同一信任边界，文档中已注明。
- 语音与"屏幕内容"同属隐私敏感数据，不落盘、不录制。

## ADR-016：控制流与视频流解耦，控制通道独立重连

**日期**：2026-10-20
**状态**：已采纳

**决策**：控制流与视频流各自建立、各自维护。控制通道断开时**只重建控制通道**，
视频解码与画面不受影响；如果发现连接总是"空闲一段时间后被断开"，再按观测值
自动启用空闲心跳（周期取观测值的一半）。

**理由**：控制通道在不操作时是安静的，视频通道一直有数据。任何中间环节对空闲长连接
不友好，先死的必然是控制通道。实际踩到过两次：

1. 调试用 `tools/tcp-relay.py` 在 `create_connection(timeout=5)` 之后没有清掉超时，
   导致上游 `recv` 每 5 秒超时一次并关掉转发——表现为"用着用着控制不了，画面却正常"；
2. 公网路径上的 NAT / 代理也可能回收空闲表项。

如果把两条流绑在一起重连，控制一断画面就闪断，用户只会以为软件不稳定。

**放弃的备选**：
- 固定心跳：scrcpy 控制协议没有 ping，唯一的无副作用消息是 `RESET_VIDEO`，
  它会强制产生关键帧；固定周期会白白耗流量和电量。
- 断线后整场会话重连：画面闪断，代价过大。

**影响**：
- 控制器新增 `ControlLink`（独立连接 + 重连 + 自适应心跳）、`Channels`（两条流共用的建立/握手）。
- 调试工具里的超时 bug 已修（`tools/tcp-relay.py`：连接成功后 `settimeout(None)`）。

## ADR-015：中继节点使用 Rust 实现

**日期**：2026-10-20
**状态**：已采纳（替换 `tools/relay-server.py`）

**决策**：中继服务改用 Rust（`relay/`，tokio），编译为单个二进制部署；
线上协议保持 v2 不变（`AGENT / FIND / DATA`、常连接 + 按需开流），两端 App 无需改动。

**理由**：节点上少一个 Python 运行时与一堆脚本；单文件部署、内存占用小、
连接生命周期可控（tokio 任务 + 超时/心跳语义清晰）。协议不变，替换风险低。

**放弃的备选**：
- 继续用 Python：需要解释器，线程模型在连接多时不好观测。
- 换成 Go：同样可行，但本机与协作环境已有 Rust 工具链，且能写同语言的端到端测试。

**影响**：
- `relay/` 自带 4 个端到端集成测试（配对、双角色隔离、长辈端离线、信令替换）。
- 部署脚本 `tools/deploy-relay.sh`：上传源码 → 节点编译 → 安装二进制 → 清理工具链与构建产物
  （Rust 编译缓存很占磁盘，节点盘小，必须清）。
- 文档 `docs/ops/relay-node.md` 已同步。

## ADR-014：固定使用 Shizuku 13.5.4（13.6.0 在联发科机型上不可用）

**日期**：2026-10-19
**状态**：已采纳

**决策**：长辈端要求安装 **Shizuku 13.5.4**，不使用 13.6.0；部署前必须在目标机型上
实测 UserService 能否启动。

**理由**：实测发现 Shizuku 13.6.0 的 UserService 在**联发科机型**上启动即崩：

```
Caused by: NullPointerException at android.app.LoadedApk.makeApplicationInner
```

这是上游已知缺陷（RikkaApps/Shizuku#1198、#1171，与 Shizuku-API PR #80 有关），
并非本项目代码问题。换装 13.5.4 后立刻正常，探针完整跑通（uid=2000 shell、
app_process 拉起 scrcpy-server 成功）。测试机 Redmi K60 Ultra 为天玑 9200+。

**放弃的备选**：
- 用 13.6.0 并规避：无可行规避手段，崩溃发生在应用代码执行之前。
- 放弃 UserService 改用其它机制：Shizuku 公开 API 中 `newProcess` 已移除，
  UserService 是唯一正路。

**影响**：
- 部署手册必须写明版本要求与校验方法。
- 上游修复后可重新评估；重新评估前不改版本。
- 这条约束同时是"机型白名单"的一部分：联发科 + 新系统的机型必须实测。

## ADR-013：仓库不留任何个人与环境信息

**日期**：2026-10-18
**状态**：已采纳

**决策**：仓库中不得出现作者本人或任何使用者的可识别信息：公网/内网 IP、主机名、
SSH 密钥标识与指纹、账号名、邮箱、设备序列号、隧道密钥。文档一律使用
`<NODE_PUBLIC_IP>`、`<DEVICE_LAN_IP>` 这类占位符。

**理由**：项目开源后仓库是公开的；节点 IP 暴露等于把攻击面与"这台机器是谁的"一并公开。
密钥一旦进仓库，历史里就再也删不干净。

**执行方式**：
- `.gitignore` 忽略 `.secrets/`（存放本地实例信息、密钥、二维码）。
- `tools/check-personal-data.sh` 在提交前扫描：公网 IP、内网 IP、私钥块、
  已知的设备名/账号名。已接入 git pre-commit hook。
- 已对工作区与历史做了一次清洗（含一条历史提交）。

**影响**：任何人 clone 后都需要自己生成占位符对应的真实值，见
`docs/ops/node-wireguard.md` 与 `tools/setup-node.sh`。

## ADR-012：以 Apache-2.0 开源，目标是"别人能自己搭一套"

**日期**：2026-10-18
**状态**：已采纳（取代 ADR-001 的"仅自用"）

**决策**：项目开源，许可证 Apache-2.0。任何人可自行搭建节点、部署长辈端、编译两端 App。

**理由**：
- 依赖的上游都是 Apache-2.0（scrcpy、scrcpy-server、ScrcpyForAndroid），
  Apache-2.0 与它们兼容且含专利授权条款。
- 这类工具的价值在于"自己掌控自己的数据"；只有能自托管，才谈得上隐私。

**配套要求**（列入验收）：
- 节点一键脚本 `tools/setup-node.sh`，任意 Debian/Ubuntu VPS 可用。
- 长辈端部署手册面向非开发者可执行。
- 所有配置项不得硬编码个人基础设施；端点、端口、密钥由配置或脚本生成。
- **无遥测、无统计上报、无第三方分析 SDK**。
- 保留上游署名（见 `NOTICE`），fork 部分保留原许可证与版权声明。

**放弃的备选**：AGPL（对自用场景无实际收益，且与上游许可组合更复杂）；GPL（同上）。

**影响**：ADR-001 中"不上架、不分发"的结论作废；但"不走应用商店"仍然保留——
分发方式为源码 + 自编译 APK。

## ADR-011：跨公网用 WireGuard hub，暂不做打洞

**日期**：2026-10-18
**状态**：已采纳

**决策**：M1 用 WireGuard 组网，节点做 hub，两端各拿固定隧道 IP。

**理由**：
- 30 分钟可落地，加密由网络层解决，应用层不用碰 TLS。
- 实测新加坡节点到国内 32ms、出口 766Mbps，带宽与延迟都可接受。
- 两端配置分流（`AllowedIPs = 10.66.66.0/24`），不影响长辈手机正常上网。

**放弃的备选**：headscale + DERP（更复杂，M3 再评估）；自研反向隧道（要写中继服务）；
WebRTC（会重新引入 MediaProjection 依赖）。

## ADR-010：控制端 fork ScrcpyForAndroid，而不是自研

**日期**：2026-10-18
**状态**：已采纳

**决策**：`controller/` 目录 fork `Miuzarte/ScrcpyForAndroid`，只替换连接层。

**理由**：
- Apache-2.0，可自由修改与分发。
- 它的传输层（`nativecore/DirectAdbClient` 等）与解码渲染层（`MediaCodecVideoDecoder`、
  `PersistentVideoRenderer`）是分开的，替换面清晰。
- 它把 scrcpy 的 C 客户端编进 App（NDK + `NativeCoreFacade`），协议正确性由上游保证。
- 已实现中文输入、剪贴板、旋转、录制等我们本来要花大力气做的功能。

**放弃的备选**：自研 Kotlin 客户端（工作量最大、协议细节最容易出错）。

**影响**：引入较大的第三方代码量，需要维护 fork 关系，只改 `nativecore/AgentClient`。

## ADR-009：长辈端自研极简 App + Shizuku

**日期**：2026-10-18
**状态**：已采纳

**决策**：长辈端装一个自研 App，经 Shizuku 以 shell 身份启动 scrcpy-server，暴露两条
流；不顺带依赖无线调试常开。

**理由**：
- 上游方案要求"无线调试常开"，重启后可能被系统关闭，老人无法自行恢复。
- Shizuku 在 Android 13+ 可借"可信 WLAN"自启，是唯一能做到"老人零操作"的路径。
- 不 root。

**放弃的备选**：无线调试常开（安全面大、易失效）；开机自动开 adb 脚本（等同长期暴露
adbd）；root（刷机风险）。

**风险**：Shizuku 自启在部分 ROM 上不可靠 —— 列为 M1 第一优先验证项。

## ADR-008：确认服务器归属，接受新主机密钥

**日期**：2026-10-18
**状态**：已采纳

**决策**：接受 `<NODE_PUBLIC_IP>` 的新 ED25519 主机密钥
（`SHA256:8GT9JH/9B77lOoRdMEDoqsrTWdDpoq6X1tPMyXwUnSo`）。

**理由**：服务器 `authorized_keys` 中存在账号主人的公钥，与本地 `id_ed25519.pub`
指纹一致；服务器上的运维痕迹（安装脚本、命令历史时间戳）也指向账号主人本人。
密钥变化源于 2026-09 底的重装系统。

**确立的规则**：接受主机密钥变更前必须取得独立证据；"能连上"不等于"是同一台机器"。

**日期**：2026-10-18
**状态**：**已被 ADR-012 取代**（2026-10-18 起项目改为 Apache-2.0 开源、可自托管）

**决策**：自用、不上架、不分发。

**理由**：用户明确。因此应用商店审核、ICP/APP 备案、软著等不适用；但保留安全实践
（绑定白名单、可见提示、一键结束、不落盘）。
